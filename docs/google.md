# Google account connection

> `crates/calendar-google` implements OAuth (PKCE, loopback), token refresh/revoke, the Calendar REST client and the Google-to-core mapping. `crates/calendar-sync` implements the Credential Manager vault, the SQLite cache with sync tokens and write journal, the sync engine and the polling schedule. Both are tested against fake HTTP, in-memory SQLite and a test-owned Credential Manager service only. `service.rs` connects them to the UI, and nothing has run against a real Google account. See [architecture](architecture.md).

Calendar connects multiple Google accounts and groups calendars by account. Writable calendars support creation, editing, moving and resizing events. Reader calendars and special Google event types remain read-only. Sample data is removed on startup.

## Configure once

1. In [Google Cloud](https://console.cloud.google.com/), create/select a project and enable **Google Calendar API**.
2. Configure **Google Auth Platform** branding/audience. For personal testing, keep the external app in Testing and add your Google email as a test user.
3. Create an OAuth client with application type **Desktop app** (not Web application). Export its client ID and secret in the shell that builds the app (`.env.example` lists the names):

```bash
export GOOGLE_CLIENT_ID=your-client-id.apps.googleusercontent.com
export GOOGLE_CLIENT_SECRET=your-desktop-client-secret
```

The values are compiled into the executable with `option_env!`, so they are read at build time; a value in the process environment at launch overrides the embedded one (development only). Nothing loads a `.env` file. If neither source has both values, `Config::from_environment()` returns `None` and the UI must show "sign-in is not configured in this build"; nothing else fails.

Do not commit credentials or paste them in chat. Google documents that the secret of a Desktop-app client cannot be kept confidential once it ships in an executable, so treat it as an identifier, not proof of app identity. PKCE (S256, verifier never leaves the process until the token exchange) is what protects the authorization code. An executable built with real values contains them. CI embeds the repository secrets `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` only in builds from `main`, which are the published release; pull-request artifacts are built without them.

4. Restart with `bash scripts/start.sh`. Open the profile circle, then **Settings → Google accounts → Add Google account**. Complete consent in your browser (`open_in_browser` starts the default browser through `rundll32 url.dll,FileProtocolHandler`).

The callback binds a temporary random port on `127.0.0.1`; Desktop clients support this without manually configuring a web redirect URI. Sign-in expires after five minutes. **Cancel sign-in** ends the pending flow without touching existing accounts. **Disconnect** removes the local credential and every cached row of the account first, then attempts a best-effort revoke at Google; if Google is unreachable the local data is already gone and the grant can be removed in your Google account. Signing in with an account that is already connected replaces its stored credential instead of adding a second account. A build without `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` shows "Sign-in is not configured in this build." and still lists cached accounts and events.

## Credentials and permissions

The requested scopes are `calendar.calendarlist.readonly` and `calendar.events` under `https://www.googleapis.com/auth/`, plus `openid email profile` for the name and avatar. Existing accounts use **Reconnect** in Settings and complete browser consent again. A timed-out or denied consent preserves the existing connection.

Refresh tokens go into Windows Credential Manager (`calendar-sync::vault`): one generic credential per account, target `calendar.google.local/<account_id>` (`account_id` is Google's `sub`), holding only the refresh token and the granted scopes, persisted for the local machine. Access tokens live in memory. Tokens are excluded from SQLite, `.env` and logs. Profile data (email, name, picture URL) lives in the cache's `accounts` table.

The cache is `%LOCALAPPDATA%\Calendar\calendar.db` (`CALENDAR_DATA_DIR` overrides the directory), never relative to the working directory. It runs in WAL mode with a 5 s `busy_timeout`, so the tray and the window can open it at the same time, and every write transaction is short. It holds event content, so it is not something to share.

Google testing-mode grants may expire after seven days; reconnect if the app reports that authorization expired or was revoked. Public distribution requires Google consent-screen/verification work appropriate to the scopes requested.

## Validation

The callback is a short-lived loopback listener (`std::net::TcpListener` on `127.0.0.1`, random port, polled while the sign-in waits) protected by a one-use random state and S256 PKCE. A wrong-state request is answered with 400 and ignored without consuming the flow; a matching request ends it, and the listener closes, so a replay finds nothing listening.

`crates/calendar-google` tests (fake HTTP on localhost, Google is never called) cover the RFC 7636 PKCE vector and that the token request's verifier matches the URL's challenge, wrong state, denied consent, state single use, a real loopback callback, cancel and timeout, a repeat sign-in being flagged (`already_connected`, matched on Google's `sub`), refresh and revoke, calendar-list and event pagination, `410 Gone`, ETag conflicts, retried operation ids, and mapping edge cases (midnight, exclusive all-day end, DST). Live consent, credential-vault persistence and real Google behavior (including the unverified points below) must be verified with your configured Google project and account.

References: [Google Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [Calendar list API](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list).

## Event sync and offline viewing

The desktop reads the SQLite cache that `calendar-sync` keeps up to date with `syncToken` polling (see [architecture](architecture.md)); the views never call Google. `calendar-google` provides the building blocks:

- `sync_events` with `EventQuery::Full { time_min, time_max }` (first sync or after `Error::Gone`) and `EventQuery::Incremental { sync_token }`. Both send `singleEvents=true`, `maxResults=250` and a `fields` mask, follow `nextPageToken`, and return the last page's `nextSyncToken`. Per Google, `timeMin`/`timeMax` are forbidden with `syncToken`, so the bounds apply to the full sync only. Any failed page fails the whole call; a failure is never an empty result.
- `410 Gone` is `Error::Gone`: drop that calendar's token and cache and run a full sync.
- Cancelled events (tombstones with only an id) and events that are no longer displayable become `EventChange::Deleted`; apply changes in order.
- Event ids are `google:<base64url calendar id>:<provider id>`; recurring instances keep Google's `<series>_<instant>` id and expose `recurring_event_id`. The sync layer must namespace `calendar_id` by account so a calendar shared between two accounts stays separate.
- All-day end dates stay exclusive. Date-only values map to the first valid instant of that date in the cache zone (`Google::set_display_zone`), also when a DST gap swallows midnight, and are written back as dates in that zone. The cache zone is the Windows system zone, read as an IANA name from `Windows.Globalization.Calendar` (Windows' own ICU data, no mapping table here) at the start of every sync run in both the tray and the window, and recorded in the cache `meta` table. When the system zone differs from the recorded one, one short transaction drops every calendar's sync token and records the new zone, so each calendar does a full sync that rebuilds its all-day rows; cached events stay visible until it finishes (all-day cards may sit a few hours off until then, or while offline). If Windows cannot name the zone, the recorded zone stays in force, else UTC, with a warning in the log and nothing recorded. Writes use the recorded zone, and the window and the tray render with it, so they cannot disagree.
- Cached events are isolated by account and calendar; disconnect clears them; failed refreshes retain cached events and show an error. Those parts belong to `calendar-sync` (below).

### Cache window and sync tokens (`calendar-sync`)

What the documentation says: events.list lists `timeMin` and `timeMax` among the parameters that "cannot be specified together with `nextSyncToken`", and with a sync token `showDeleted` cannot be false ([events.list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list)). The sync guide says "Sync tokens aren't compatible with most filters, but you may want to limit your full sync to only a certain date range" (its sample sets `timeMin` on the full sync), that every list request should use the same set of query parameters including the initial one, that an incremental result always contains deleted entries, and that `410` means wipe and run a full sync ([sync guide](https://developers.google.com/workspace/calendar/api/guides/sync)). Neither page says whether an incremental result honours the window of the full sync that produced its token, nor how far `singleEvents=true` expands an unbounded recurring series.

The design therefore does not depend on either answer:

- The first sync of a calendar (and every resync) is a full sync with both bounds: `timeMin` = now − 30 days, `timeMax` = now + 180 days, `singleEvents=true`. The window is stored with the calendar. Bounding both ends is the only way to cap recurring-series expansion that the documentation lets us rely on.
- Incremental syncs send only `syncToken` (plus the same `singleEvents`/`fields`) and store whatever Google returns.
- After each sync run, events that ended more than 30 days ago are deleted, so the past edge never grows.
- When fewer than 60 days of the stored window are left, the next sync of that calendar is a fresh full sync with a new window, which replaces the calendar's events in one transaction. That is about one full sync per calendar every 120 days.
- A `410` clears the calendar's token (cached events stay visible), then runs the full sync; if that fails, the next attempt starts from the full sync again.
- A deletion also removes cached instances whose `recurring_event_id` equals the deleted id, in case Google reports a whole series as one tombstone. The reference says that with `singleEvents` and `showDeleted` Google returns instances of deleted events, not the series.
- Calendars come from `calendarList` on every run; one that disappeared is removed with its events and state. A failed list or event fetch keeps the cache and is returned as an error for that account; one failing calendar does not stop the others.

Cost (estimate, not measured on real data): a cached event is roughly 200–400 bytes in SQLite (a synthetic 2000-event file with 200-character descriptions measured 0.76 MB), so a busy calendar with a few thousand expanded events over the 210-day window is under 1 MB on disk. Full-sync results are held in memory once per calendar while paging, about 1–2 MB for a few thousand events, then freed. Each poll costs one `calendarList` request per account plus one incremental request per calendar.

Not verified against real Google (unconfirmed in the documentation or only exercised against fakes), each needing one run with a real account: that a full sync bounded by both `timeMin` and `timeMax` still returns a `nextSyncToken` (if it does not, `sync_events` fails with `InvalidResponse` rather than storing nothing); whether incremental results include events outside the original window (the cache keeps them until the next re-bound or the past-edge prune); whether `singleEvents=true` combined with `syncToken` reports a deleted series as instance tombstones or as one master tombstone (both are handled); the exact `fields` mask syntax (`extendedProperties/private`); whether the delete endpoint returns `410` for an already deleted event; and whether a calendar's colour or access-role change reaches cached events before they next change (it does at the next re-bound).

### Sync schedule (`calendar-sync::scheduler`)

One plain thread blocks on a channel with a timeout equal to the time until the next poll. The caller picks the mode once (`WindowOpen`: 60 s in the UI process, `TrayIdle`: 300 s in the tray process) and sends `SyncNow` for window open, window focus and the tray "Sync now" item. The tray skips its poll while the UI process runs. A sync runs on that same thread, so two can never overlap, and a trigger within 5 s of a finished sync is skipped; triggers that arrive while a sync runs therefore join its result. The intervals are starting values to tune against measured request volume and battery use.

## Writes (`calendar-sync::sync::write`)

`Syncer::write` takes a `WriteRequest` (`account_id`, `calendar_id`, a caller-chosen `operation_id`, and a `Change`: `Create(draft)`, `Update { event, expected_revision }` or `Delete { event_id, expected_revision }`). It runs on the sync thread, one write at a time and never during a poll.

Flow: a repeated `operation_id` is answered from the `operations` journal first (applied: the stored result, failed: `NotApplied`, pending or uncertain: settled by reading, below), so a retry never sends a second request. Otherwise the checks that need no network run: calendar role, event type, recurring scope, validation, and staleness (`expected_revision` is the `revision` the user was looking at; the cache having moved on is `Stale` and nothing is sent). Then the operation is journaled `Pending`, the request is sent, and the outcome is recorded together with the event Google returned in one short transaction, so the cache and the journal cannot disagree after a crash.

- Creates use a stable provider id derived from the draft's UUID (`created_event_id` tells the cache id in advance) and write the operation id into the private extended property `calendarOperation`. A `409` on retry is reconciled by reading the event and comparing that marker.
- Updates (including move and resize) PATCH with `If-Match` set to the cached ETag; a `412` is stale unless the stored event already carries the same operation id. Deletes send `If-Match`; an already deleted event counts as done.- A stale write (`412` or an `expected_revision` mismatch) is `WriteError::Stale`. After a `412` the newer event is read and put in the cache, so the user sees what they would have overwritten; nothing is overwritten silently.
- Read-only calendars (any role except owner or writer) and read-only events (birthdays, focus time and other special types) are `ReadOnly` before anything is sent or journaled. Insufficient grants come back from Google as `InsufficientPermissions` and fail the operation.
- Recurring events: single events and one occurrence of a series are supported. Instances are patched or deleted by their own instance id, which changes that occurrence only. A series id (recognised because cached instances name it as `recurring_event_id`) is `SeriesEdit`; series-wide edits and recurrence rules are not exposed. Guests receive Google's update notifications (`sendUpdates=all`); attendee management is not exposed.
- Outcomes: a certain failure (4xx, no credential, token refresh failed before sending) is `Failed` and nothing changed. A timeout or connection error, a 5xx, or an unreadable answer is `Uncertain` and `WriteError::Unknown`: the write may have been saved.

Uncertain and crashed (`Pending`) operations are never replayed. The journal stores no event content, so the sync of the account settles them first, before listing calendars: it reads the event by its id and decides from the `calendarOperation` marker (create and update are applied when the stored event carries this operation id; delete when the event is gone), refreshes the cached event from what it read, and records `Applied` or `Failed`. A repeat of the same `operation_id` settles it the same way. If Google cannot be asked, the operation stays open for the next sync. The marker is compared instead of the ETag because the journal keeps no ETag and the marker is exact. A payload column would allow resending after a restart, but resending is what the rules forbid for unknown outcomes, and it would store event content a second time; the cost of the choice is that after an app restart a draft whose write failed is not recoverable, so a form must keep its draft in the running process until the outcome is `Applied`. Finished journal rows older than seven days are pruned.

Background syncs never touch the journal: `Store::pending_operations()` (published as `Snapshot::pending`, with view-key event ids) lists the unknown outcomes, and a sync that arrives while one is open leaves it listed. The cache holds only what Google has confirmed, so a view keeps its optimistic placement of an event while it is pending and drops it when the entry leaves the list. After a failed write, a retry is a new action: new `operation_id` (and a new draft UUID for a create).

Tested against fake HTTP only: retries with one operation id, stale ETags, uncertain creates settled to applied and failed, uncertain updates and deletes, rejected writes leaving the cache untouched, read-only calendars and events, one occurrence versus a series, two accounts with the same calendar and draft, and a poll arriving while a write is pending. Not verified against real Google: that `If-Match` on PATCH and DELETE of an event behaves as documented for these accounts, that `extendedProperties.private` survives a PATCH made by other clients, that an instance PATCH creates the exception without touching the series, and the status Google returns when reading a deleted event (`404`, `410` and a cancelled body are all treated as gone).

Settings have two pages: General (Monday/Sunday week start, which re-aligns the shown week; all-day events in the tray list; the read-only system display zone) and Google accounts. Notifications, start with Windows, working hours, global shortcut and sync intervals have no controls because the features do not exist. Each account lists its three grants separately (calendar list, event reading, event editing) and the last refresh error. Events are created, edited, moved, resized and deleted through `Handle::write` (editor form, event popover, drag on the timeline, the New button). Only the title, calendar, start and end, all-day, location and notes are editable; attendees, recurrence, conferencing and reminders are not offered. A recurring event is edited one occurrence at a time and the popover and form say so. Read-only calendars and events, and accounts without the editing grant, block the write in the view with the reason. Saving shows the new placement at once and keeps it until Google answers; a failure restores the old placement and shows the reason (the form keeps its draft while the app runs), `Stale` shows the newer version, and an unknown outcome keeps the placement and says the change may have been saved until the sync settles it. Not verified with a real Google account. T/W/M navigate to the current week, week view and month view. Preferences live in `preferences.json` in the data directory (`CALENDAR_DATA_DIR` or `%LOCALAPPDATA%\Calendar`); a missing or corrupt file gives the defaults. The display zone is the compile-time `DISPLAY_ZONE` shared by the UI and the tray. The desktop starts at its 1050 × 680 minimum size and uses bundled Inter throughout.
